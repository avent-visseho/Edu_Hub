# SYSTÈME INTÉGRÉ DE GESTION DE L'ÉDUCATION AU BÉNIN

## Spécification fonctionnelle, métier, données et architecture du prototype

### Version 1.0 — Prototype de démonstration

---

# 1. RÉSUMÉ DU PROJET

Le projet consiste à développer une plateforme numérique intégrée permettant de gérer, dans un système unique, l'ensemble des processus liés à l'éducation.

La plateforme couvrira progressivement :

* l'éducation préscolaire ;
* l'enseignement primaire ;
* l'enseignement secondaire général ;
* l'enseignement technique ;
* la formation professionnelle ;
* l'alphabétisation ;
* l'enseignement supérieur ;
* la recherche ;
* les examens ;
* les concours ;
* les certifications ;
* l'orientation ;
* les bourses ;
* les aides sociales ;
* les enseignants ;
* les établissements ;
* les parents ;
* les infrastructures ;
* les transports ;
* les bibliothèques ;
* les ressources pédagogiques ;
* les projets ;
* les stages ;
* l'emploi ;
* les statistiques ;
* la gouvernance ;
* l'accessibilité ;
* l'inclusion ;
* l'analyse de données ;
* l'intelligence artificielle.

Le prototype sera entièrement autonome.

Il ne dépendra :

* d'aucune API EducMaster ;
* d'aucune API ministérielle ;
* d'aucune base de données gouvernementale ;
* d'aucun service externe obligatoire.

Toutes les données utilisées dans le prototype seront **fictives ou générées automatiquement**.

---

# 2. OBJECTIF DU PROTOTYPE

L'objectif n'est pas de produire immédiatement un système national en production.

L'objectif est de produire une **simulation fonctionnelle extrêmement complète** permettant de démontrer ce que pourrait devenir une plateforme numérique nationale de l'éducation.

Le prototype doit donner l'impression d'utiliser un véritable système national.

Un démonstrateur doit pouvoir montrer :

> Un étudiant est inscrit dans un établissement, possède un dossier scolaire, reçoit ses bulletins, suit ses cours, possède des notes, passe des examens, obtient des résultats, peut demander une bourse, utiliser le transport universitaire, rejoindre un projet, effectuer un stage et finalement entrer dans le monde professionnel.

En parallèle :

> Un enseignant gère ses classes, ses cours, les présences, les notes et les bulletins.

Et :

> Un établissement gère ses élèves, ses enseignants, ses classes, ses salles, ses examens, ses résultats et ses infrastructures.

Enfin :

> Une administration peut interroger l'ensemble des données et produire des analyses extrêmement précises.

---

# 3. PHILOSOPHIE DU PROJET

Le système repose sur cinq principes.

## 3.1. Tout gérer

Aucun domaine important de la vie éducative ne doit être volontairement exclu du modèle.

---

## 3.2. Tout simuler

Les données réelles ne sont pas nécessaires pour la démonstration.

Le système possède son propre générateur de données fictives.

---

## 3.3. Tout relier

Les modules ne doivent pas fonctionner comme des applications indépendantes.

Exemple :

```text
Élève
  ↓
Établissement
  ↓
Classe
  ↓
Enseignant
  ↓
Matière
  ↓
Notes
  ↓
Moyenne
  ↓
Bulletin
  ↓
Examen
  ↓
Résultat
  ↓
Orientation
```

---

## 3.4. Tout rechercher

L'administration doit pouvoir interroger les données de manière très avancée.

Exemple :

> « Afficher tous les élèves des CEG de l'Atlantique ayant une moyenne générale supérieure ou égale à 18/20. »

Ou :

> « Quels sont les établissements ayant un taux de réussite inférieur à 50 % au BEPC ? »

Ou :

> « Quels établissements du Littoral ont plus de 1 000 élèves mais moins de 20 salles ? »

Ou :

> « Quels élèves ont une progression supérieure à 3 points entre le premier et le troisième trimestre ? »

---

## 3.5. Accessibilité universelle

Le système doit pouvoir être utilisé par :

* une personne voyante ;
* une personne malvoyante ;
* une personne aveugle ;
* une personne sourde ;
* une personne ayant des difficultés de lecture ;
* une personne peu alphabétisée ;
* un utilisateur disposant d'une connexion faible.

# 152. VISION À LONG TERME

Le prototype est volontairement autonome.

Il ne dépend d'aucun système externe.

Mais son architecture doit être suffisamment propre pour qu'un jour :

```text
DONNÉES FICTIVES
      ↓
DONNÉES RÉELLES
      ↓
MIGRATION
      ↓
SYSTÈME NATIONAL
```

puisse être réalisée progressivement.

Le prototype doit donc être considéré comme :

> **une simulation complète du futur système, et non comme une simple maquette graphique.**

---

# 153. CONCLUSION

Le projet devient ainsi un **système d'information éducatif complet**.

Il reprend le périmètre fonctionnel observable d'EducMaster et les processus détaillés dans les documents fournis, notamment la chaîne ministère → DEC → DDEPS → établissement → candidat, la gestion des examens, séries, matières, pièces jointes, centres, salles, candidats, notes, moyennes, jurys, contentieux, budget et archives.
Il reprend également les dimensions de gestion scolaire d'EducMaster : apprenants, enseignants, établissements, classes, examens, emplois du temps, ressources humaines, statistiques et cartographie.

La différence fondamentale est que notre prototype **ne s'arrête pas à la gestion scolaire**.

Il couvre :
